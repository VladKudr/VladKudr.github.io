MCP в 3D

Как устроены сервисы на Model Context Protocol: из каких частей они состоят, как передают сообщения и как их проектировать. Рядом с текстом — живая 3D-модель: главы листаются как страницы книги, а схемы на каждой странице анимированы.

    Глава 1

    Зачем нужен MCP

    До MCP каждое AI-приложение подключало каждый сервис по-своему. Если есть M приложений и N сервисов, то нужно M×N интеграций, и каждую надо написать, протестировать и чинить при каждом изменении API.

    MCP — это открытый стандарт «разъёма» между AI-приложением и внешним миром. Приложение один раз реализует клиент, сервис один раз реализует сервер, и после этого любой клиент работает с любым сервером. Похожую задачу для редакторов кода когда-то решил Language Server Protocol, и авторы MCP прямо ссылаются на него как на образец.

    Смотрите на модель

    анимация по шагам
    1. Без стандарта: 3 приложения × 4 сервиса = 12 уникальных адаптеров. У каждого своя авторизация, свои форматы и ошибки.
    2. С MCP: 3 клиента + 4 сервера. Все говорят на одном протоколе, и новое приложение сразу получает доступ ко всем серверам.

    Что именно стандартизирует MCP

    • Формат сообщений: JSON-RPC 2.0 с обязательными метаданными (_meta).
    • Возможности сервера: инструменты (tools), данные (resources) и шаблоны промптов (prompts).
    • Как сервер может спросить клиента о недостающем: например, попросить пользователя заполнить форму.
    • Транспорты (stdio и Streamable HTTP) и авторизацию на базе OAuth 2.1.
    Чего MCP не решает. Какую модель использовать, как host строит промпт и интерфейс, как именно модель выбирает инструмент. Это остаётся на стороне приложения.
    Глава 2

    Архитектура: Host, Client, Server

    В MCP три роли. Их легко спутать, поэтому посмотрите на модель: синяя «коробка» — это host, бирюзовые кубики внутри неё — клиенты, фиолетовые стойки — серверы.

    РольЧто делает
    HostAI-приложение, с которым работает человек: чат-ассистент, IDE, агент. Создаёт клиентов, управляет моделью, собирает контекст и спрашивает согласие пользователя.
    ClientКомпонент внутри host. Каждый клиент связан ровно с одним сервером (1:1) и прикладывает версию протокола и свои возможности к каждому запросу.
    ServerПрограмма, которая даёт контекст и возможности: инструменты, данные, промпты. Бывает локальным процессом (stdio) или удалённым сервисом (Streamable HTTP).

    Пройдёмся по модели

    нажмите на шаг
    1. Host координирует всё: запускает клиентов и решает, что показать модели и что разрешить.
    2. У каждого сервера свой клиент. Три сервера — три клиента.
    3. Локальный сервер запускается host-ом как дочерний процесс и общается через stdin/stdout.
    4. Удалённый сервер — это обычный веб-сервис с одним MCP-эндпоинтом и авторизацией OAuth.
    5. За сервером стоит реальная система: файлы, база данных, API. Сервер переводит её на язык MCP.
    6. Модель не подключается к серверам напрямую. Host решает, какие инструменты и данные попадут в её контекст.
    Изоляция как принцип. Спецификация требует, чтобы сервер не видел весь разговор и не мог «заглянуть» в другие серверы. Контекст между ними переносит только host, и только с согласия пользователя.

    Принципы, заложенные в дизайн

    • Серверы должны быть простыми. Оркестрацию, UI и работу с моделью берёт на себя host.
    • Серверы должны легко комбинироваться: каждый делает своё, и их можно подключать пачками.
    • Возможности наращиваются постепенно. Стороны сообщают друг другу, что умеют (capabilities), а необязательные функции подключаются через расширения.
    Глава 3

    Два слоя: данные и транспорт

    MCP разделён на два слоя. Data layer отвечает за то, что говорим: сообщения JSON-RPC 2.0, методы и примитивы. Transport layer отвечает за то, как доставляем: канал, фрейминг, заголовки, авторизацию. Сообщения одинаковы на любом транспорте.

    Путь сообщения через стек

    нажмите на шаг, чтобы увидеть JSON
    1. Запрос содержит id, method и params. На него обязательно придёт ответ. 
      {
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": { "city": "Казань" },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {},
      "io.modelcontextprotocol/clientInfo": { "name": "my-agent", "version": "1.0.0" }
    }
  }
}
    2. Ответ несёт тот же id и либо result, либо error. В версии 2026-07-28 у каждого result есть поле resultType. 
      {
  "jsonrpc": "2.0",
  "id": 3,
  "result": {
    "resultType": "complete",
    "content": [{ "type": "text", "text": "Казань: +14°C, облачно" }],
    "isError": false,
    "_meta": {
      "io.modelcontextprotocol/serverInfo": { "name": "weather", "version": "2.0.1" }
    }
  }
}
    3. Уведомление приходит без id, и отвечать на него не нужно. Например, клиент сообщает, что запрос больше не нужен. 
      {
  "jsonrpc": "2.0",
  "method": "notifications/cancelled",
  "params": {
    "requestId": 3,
    "reason": "Пользователь нажал «Стоп»"
  }
}
    4. Ошибка протокола — это ответ с error вместо result, например на вызов несуществующего инструмента. 
      {
  "jsonrpc": "2.0",
  "id": 4,
  "error": {
    "code": -32602,
    "message": "Unknown tool: get_wether"
  }
}
    Важно: запросы отправляет только клиент. В версии 2026-07-28 сервер больше не шлёт клиенту запросов, только ответы и уведомления. Если серверу что-то нужно от клиента, он говорит об этом в ответе (глава 7).

    Коды ошибок

    КодЗначение
    -32700 … -32603Стандартные коды JSON-RPC: parse error, invalid request, method not found, invalid params, internal error.
    -32602Invalid params. С этой версии так же отвечают на «ресурс не найден» (раньше был -32002).
    -32020HeaderMismatch: HTTP-заголовок не совпадает с телом.
    -32021MissingRequiredClientCapability: запросу нужна возможность клиента, которую тот не заявил.
    -32022UnsupportedProtocolVersion: сервер не знает версию клиента.

    Диапазон -32000…-32019 отдан реализациям, а -32020…-32099 зарезервирован за спецификацией MCP.

    Глава 4

    Жизненный цикл: протокол без сессий

    Главное изменение версии 2026-07-28: MCP стал stateless. Рукопожатия initialize больше нет, и серверу не нужно помнить соединение, потому что каждый запрос самодостаточен.

    Версия протокола и возможности клиента передаются в _meta каждого запроса. Поэтому любой запрос может попасть на любую реплику сервера за балансировщиком, как обычный REST-вызов, и «липкие» сессии не нужны.

    Смотрите на модель

    каждый запрос уходит на свою реплику
    1. Клиент может заранее спросить сервер, какие версии и возможности тот поддерживает. Отвечать на server/discover сервер обязан. 
      {
  "jsonrpc": "2.0",
  "id": "discover-1",
  "method": "server/discover",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientInfo": { "name": "ExampleClient", "version": "1.0.0" },
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}
    2. Сервер возвращает поддерживаемые версии, capabilities, инструкции для модели и время, на которое ответ можно закэшировать. 
      {
  "jsonrpc": "2.0",
  "id": "discover-1",
  "result": {
    "resultType": "complete",
    "supportedVersions": ["2026-07-28"],
    "capabilities": { "tools": {}, "resources": {} },
    "instructions": "Сервер погоды: прогнозы и история наблюдений.",
    "_meta": {
      "io.modelcontextprotocol/serverInfo": { "name": "ExampleServer", "version": "1.0.0" }
    },
    "ttlMs": 3600000,
    "cacheScope": "public"
  }
}
    3. Следующий запрос уходит на другую реплику. Это нормально: всё нужное есть в самом запросе. 
      {
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/list",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": { "elicitation": { "form": {} } }
    }
  }
}
    4. Список инструментов не зависит от соединения. Сервер отдаёт его в стабильном порядке и с подсказкой для кэша.
    5. Вызов инструмента попадает на третью реплику. Если у инструмента есть состояние (например, «корзина»), он возвращает handle, и клиент передаёт его в следующие вызовы как обычный аргумент.
    6. Ответ готов. Серверу не пришлось ничего помнить между запросами.

    Было → стало

    До 2026-07-28Сейчас
    initialize → ответ → notifications/initializedРукопожатия нет, версия и capabilities едут в _meta каждого запроса
    Заголовок Mcp-Session-Id, сессия на сервереСессий нет, состояние передаётся явными handle в аргументах
    ping для проверки связиУдалён
    Серверные запросы к клиентуMulti Round-Trip Requests (глава 7)

    Если сервер не знает версию клиента, он отвечает ошибкой -32022 со списком поддерживаемых версий, и клиент повторяет запрос с подходящей:

    { "code": -32022, "message": "Unsupported protocol version",
  "data": { "supported": ["2026-07-28"], "requested": "<версия клиента>" } }
    Совместимость со старыми серверами. Клиент, который умеет обе «эпохи», сначала пробует современный запрос (на stdio это server/discover). Если в ответ приходит не современная ошибка, он откатывается на старый initialize.

    Завершение работы. На stdio клиент закрывает stdin сервера, ждёт и при необходимости отправляет SIGTERM, а затем SIGKILL. На HTTP завершать нечего, поэтому метод DELETE больше не используется.

    Глава 5

    Транспорты: stdio и Streamable HTTP

    Спецификация определяет два стандартных транспорта. stdio подходит для локальных серверов, Streamable HTTP — для удалённых. Кроме них допускаются собственные транспорты, если они сохраняют формат и правила JSON-RPC.

    Смотрите на модель

    слева локальный, справа облачный
    1. stdio: host запускает сервер как дочерний процесс и пишет в его stdin по одному JSON-сообщению на строку, без переводов строк внутри. 
      {"jsonrpc":"2.0","id":1,"method":"resources/read","params":{"uri":"file:///work/report.md","_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientCapabilities":{}}}}
    2. Сервер отвечает строкой в stdout. В stdout нельзя писать ничего, кроме MCP-сообщений: одна случайная отладочная строка ломает поток. 
      {"jsonrpc":"2.0","id":1,"result":{"resultType":"complete","contents":[{"uri":"file:///work/report.md","mimeType":"text/markdown","text":"# Отчёт за квартал…"}],"ttlMs":0,"cacheScope":"private"}}
    3. Логи пишутся в stderr: host может их показать или сохранить, и в протокол они не попадают.
    4. Streamable HTTP: у сервера один эндпоинт, и каждое сообщение отправляется отдельным POST. Метод и имя инструмента дублируются в заголовках, чтобы прокси и шлюзы могли маршрутизировать запрос, не разбирая тело. 
      POST /mcp HTTP/1.1
Host: mcp.example.com
Content-Type: application/json
Accept: application/json, text/event-stream
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: search_issues
Authorization: Bearer eyJhbGciOiJSUzI1NiIs…

{"jsonrpc":"2.0","id":7,"method":"tools/call","params":{"name":"search_issues","arguments":{"repo":"acme/web"},"_meta":{…}}}
    5. Сервер может ответить сразу JSON-ом или открыть SSE-поток, привязанный к этому запросу: сначала прогресс и логи, в конце сам ответ. 
      HTTP/1.1 200 OK
Content-Type: text/event-stream
X-Accel-Buffering: no

data: {"jsonrpc":"2.0","method":"notifications/progress","params":{"progressToken":"t-7","progress":1,"total":3}}

data: {"jsonrpc":"2.0","method":"notifications/progress","params":{"progressToken":"t-7","progress":2,"total":3}}

data: {"jsonrpc":"2.0","id":7,"result":{"resultType":"complete","content":[…]}}
    6. Последнее событие потока — это ответ на запрос, после него поток закрывается. Если связь оборвалась раньше, запрос потерян, и клиент отправляет его заново с новым id.
    7. Чтобы получать уведомления об изменениях, клиент открывает один долгий POST subscriptions/listen и сам выбирает, на что подписаться. 
      {
  "jsonrpc": "2.0",
  "id": 1,
  "method": "subscriptions/listen",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {}
    },
    "notifications": {
      "toolsListChanged": true,
      "resourceSubscriptions": ["file:///project/config.json"]
    }
  }
}
    8. Первым сообщением сервер подтверждает подписку и перечисляет, что согласился присылать. 
      {
  "jsonrpc": "2.0",
  "method": "notifications/subscriptions/acknowledged",
  "params": {
    "_meta": { "io.modelcontextprotocol/subscriptionId": 1 },
    "notifications": {
      "toolsListChanged": true,
      "resourceSubscriptions": ["file:///project/config.json"]
    }
  }
}
    9. Когда набор инструментов меняется, по этому потоку приходит уведомление, и клиент заново запрашивает tools/list.

    Правила Streamable HTTP

    ЧтоПравило
    AcceptКлиент обязан принимать и application/json, и text/event-stream.
    УведомленияСервер отвечает 202 Accepted без тела.
    ЗаголовкиMCP-Protocol-Version и Mcp-Method нужны во всех запросах, Mcp-Name — в tools/call, resources/read и prompts/get. Если заголовок расходится с телом, сервер отвечает 400 и кодом -32020.
    GET / DELETEВозвращают 405: отдельного GET-потока и завершения сессии больше нет.
    ОтменаЗакрытие SSE-потока равносильно отмене запроса.
    БезопасностьСервер обязан проверять Origin (иначе 403). Локальный сервер должен слушать 127.0.0.1, а не 0.0.0.0.
    Устарело. Транспорт HTTP+SSE из версии 2024-11-05 (отдельные эндпоинты для POST и SSE) объявлен deprecated. Новым серверам нужен только Streamable HTTP.
    Глава 6

    Что даёт сервер: Tools, Resources, Prompts

    Сервер предоставляет три вида примитивов. Они различаются прежде всего тем, кто решает их использовать.

    ПримитивЧто это · кто управляет · методы
    ToolsДействия и вычисления: «создать задачу», «выполнить запрос». Использовать их решает модель. tools/list, tools/call
    ResourcesДанные для контекста, у каждого ресурса есть URI: файл, запись, схема БД. Подмешивает их приложение. resources/list, resources/read, resources/templates/list
    PromptsГотовые сценарии и шаблоны сообщений, например слэш-команды. Выбирает их пользователь. prompts/list, prompts/get

    Кто что вызывает

    нажмите на шаг
    1. Модель видит описания инструментов и сама решает, когда вызвать какой. Так выглядит описание инструмента в tools/list: 
      {
  "name": "run_query",
  "title": "SQL-запрос (только чтение)",
  "description": "Выполняет SELECT в аналитической БД. Не более 1000 строк.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "sql": { "type": "string", "description": "Один SELECT-запрос" },
      "limit": { "type": "integer", "minimum": 1, "maximum": 1000 }
    },
    "required": ["sql"]
  },
  "outputSchema": {
    "type": "object",
    "properties": { "rows": { "type": "array" }, "rowCount": { "type": "integer" } }
  },
  "annotations": { "readOnlyHint": true, "openWorldHint": false }
}
    2. Приложение само решает, какие данные подмешать: схему БД, открытый файл, выбранную пользователем запись. 
      {
  "jsonrpc": "2.0",
  "id": 11,
  "result": {
    "resultType": "complete",
    "contents": [{
      "uri": "postgres://analytics/schema/orders",
      "mimeType": "application/json",
      "text": "{\"columns\":[\"id\",\"customer_id\",\"total\",\"created_at\"]}"
    }],
    "ttlMs": 600000,
    "cacheScope": "private"
  }
}
    3. Пользователь выбирает готовый сценарий, например «/отчёт-по-продажам». Сервер возвращает заготовленные сообщения с подставленными аргументами. 
      {
  "jsonrpc": "2.0",
  "id": 12,
  "result": {
    "resultType": "complete",
    "description": "Отчёт по продажам за период",
    "messages": [{
      "role": "user",
      "content": {
        "type": "text",
        "text": "Построй отчёт по продажам за 2026-Q3: выручка, топ-10 клиентов, динамика к Q2."
      }
    }]
  }
}

    Детали, которые важно знать

    • Аннотации инструментов — это подсказки host-у: readOnlyHint, destructiveHint, idempotentHint, openWorldHint. Если сервер не доверенный, аннотациям верить нельзя.
    • Результат инструмента — это content[] (text, image, audio, resource_link, embedded resource) плюс structuredContent, который должен соответствовать outputSchema. Для совместимости JSON стоит продублировать текстовым блоком.
    • Шаблоны ресурсов (RFC 6570) позволяют описать целое семейство URI: postgres://analytics/table/{name}.
    • Автодополнение completion/complete подсказывает значения аргументов промптов и шаблонов прямо в интерфейсе.
    • Каждая группа примитивов объявляется в capabilities: tools, resources, prompts, completions.
    Глава 7

    Когда серверу нужен человек: Multi Round-Trip

    Иногда серверу не хватает данных: нужно подтверждение пользователя, выбор варианта, вход во внешний сервис. Раньше сервер отправлял клиенту собственный запрос. Теперь он отвечает, что ему нужен ввод, а клиент повторяет исходный запрос уже с ответами. Этот паттерн называется Multi Round-Trip Requests (MRTR).

    Подтверждение опасной операции

    нажмите на шаг
    1. Модель просит применить миграцию к базе. 
      {
  "jsonrpc": "2.0",

    Авторизация: OAuth 2.1

    Для удалённых серверов MCP опирается на OAuth 2.1. MCP-сервер играет роль resource server: он проверяет токены, но не выдаёт их. Токены выдаёт отдельный authorization server, например корпоративный IdP.

    Авторизация в MCP необязательна и касается только HTTP. Локальный stdio-сервер берёт учётные данные из окружения.

    Первое подключение

    14 шагов
    1. Клиент обращается к серверу, ещё не имея токена.
    2. Сервер отвечает 401 и указывает, где лежат его метаданные и какие scope нужны. 
      HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource/mcp",
                  scope="repo:read"
    3. Клиент читает Protected Resource Metadata (RFC 9728).
    4. В метаданных указано, какой сервер авторизации выдаёт токены для этого ресурса. 
      {
  "resource": "https://mcp.example.com/mcp",
  "authorization_servers": ["https://auth.example.com"],
  "scopes_supported": ["repo:read", "repo:write"],
  "bearer_methods_supported": ["header"]
}
    5. Клиент читает метаданные сервера авторизации (RFC 8414 или OpenID Discovery).
    6. Поле issuer должно точно совпадать с адресом. Если в метаданных нет PKCE S256, клиент обязан остановиться.

  "authorization_response_iss_parameter_supported": true

    Правила, которые чаще всего нарушают

    • Проверка audience. Сервер принимает только токены, выпущенные для него самого.
    • Никакого проброса токена. Для обращения к API за собой сервер получает отдельный токен.
    • Повышение прав (step-up). Если scope не хватает, сервер отвечает 403 с error="insufficient_scope". Клиент повторно авторизуется с объединением старых и новых scope и ограничивает число повторов.
    • Учётные данные клиента привязаны к issuer. Если сменился сервер авторизации, клиент регистрируется заново.
    • Минимальные scope на старте. Остальные права запрашиваются по мере необходимости.
    Расширения авторизации. Для межсервисных сценариев есть io.modelcontextprotocol/oauth-client-credentials (client credentials, рекомендуется JWT-assertion). Для компаний есть enterprise-managed-authorization: доступ выдаёт корпоративный IdP.

    Модель угроз

    MCP даёт модели доступ к данным и к выполнению кода, поэтому у него широкая поверхность атаки. Спецификация прямо говорит, что протокол не может сам обеспечить безопасность: её обеспечивают host, клиент и сервер.

    Где прячутся угрозы

    красные кристаллы на модели
    1. Отравленный инструмент. Описание и аннотации от недоверенного сервера — это текст, который читает модель, и в нём могут быть скрытые команды.
    2. Промпт-инъекция в данных. Текст issue, письма или веб-страницы попадает в контекст. Результаты инструментов — это недоверенный ввод, а не инструкции.
    3. Проброс токена. Сервер не должен передавать полученный токен дальше: так ломаются аудит, лимиты и границы доверия.
    4. Confused deputy. MCP-прокси со статическим client_id у стороннего сервера авторизации обязан получать согласие пользователя для каждого клиента.
    5. SSRF. Вредоносный сервер указывает в OAuth-метаданных внутренние адреса. Клиенту нужны только HTTPS и блокировка приватных и зарезервированных IP, в том числе при редиректах.
    6. Компрометация локального сервера. Установка в один клик означает запуск команды на вашей машине. Клиент обязан показать полную команду и получить явное согласие, а опасные команды (sudo, rm -rf) стоит подсвечивать и запускать в песочнице.
    7. Угон state-handle. Handle (id корзины, задачи) не заменяет аутентификацию. Его надо делать случайным и привязывать к пользователю, например <user_id>:<handle>.
    8. Защита на стороне host: явное согласие на доступ к данным и вызовы, показ аргументов перед опасными действиями, изоляция серверов друг от друга.

    Чек-лист защиты

    КтоОбязанности
    Host / клиентСогласие пользователя на каждое действие с данными и каждый вызов инструмента. Показ аргументов. Подтверждение деструктивных операций. Результаты одного сервера — недоверенный ввод для другого. Проверка OAuth-URL: только http/https, без javascript: и file:.
    СерверВалидация входа, контроль доступа, rate-limit, санитизация вывода. Защита от path traversal для file://. Проверка aud. Честные аннотации. Секреты не принимаются через формы.
    ОператорМинимальные scope. Локальные серверы слушают только 127.0.0.1, у HTTP-сервера проверяется Origin. Аудит вызовов.

    Как спроектировать MCP-сервис

    Разберём сервер на слои и проведём через них запрос. Такой разрез удобно положить в основу архитектуры любого production-сервера.

    Запрос сквозь слои

    нажмите на шаг
    1. Раздвигаем слои. Снизу вверх: транспорт → авторизация → протокол → каталог возможностей → доменная логика. Сбоку идёт сквозная наблюдаемость.
    2. Транспорт принимает HTTP-запрос: TLS, проверка Origin, сверка заголовков Mcp-Method и Mcp-Name с телом.
    3. Авторизация проверяет подпись токена, срок, issuer, audience и scope. Ответы 401 и 403 формируются здесь.
    4. Протокольный слой (обычно это SDK) разбирает JSON-RPC, проверяет версию и capabilities клиента и выбирает обработчик.
    5. Каталог находит инструмент и валидирует аргументы по inputSchema. Если что-то не так, возвращает понятную ошибку с isError: true.
    6. Доменный слой выполняет операцию на языке предметной области, не на языке API.
    7. Адаптер ходит в реальную систему с собственными учётными данными.
    8. Система возвращает данные.
    9. Результат поднимается обратно: структура по outputSchema, текст для модели, serverInfo в _meta.
    10. Наблюдаемость пронизывает все слои: traceparent из _meta, метрики по инструментам и аудит, то есть кто, что и с какими аргументами вызвал.

    Чек-лист проектирования

    ТемаРешение
    ИнструментыПроектируйте от задач пользователя, а не от эндпоинтов API: «найти просроченные счета клиента» лучше, чем обёртка над GET /invoices. Меньше инструментов, но каждый понятнее.
    Имена1–128 символов, A–Z a–z 0–9 _ - ., без пробелов, уникальные в пределах сервера. Описание объясняет, когда вызывать инструмент и что он вернёт.
    СхемыУ inputSchema всегда type: "object". Инструмент без аргументов описывается как {"type":"object","additionalProperties":false}. Добавьте outputSchema и structuredContent. Не разыменовывайте сетевые $ref.
    ОшибкиПротокольные ошибки возвращаются как JSON-RPC error. Ошибки выполнения и валидации — как isError: true с текстом, по которому модель поймёт, что исправить.
    СостояниеНикакого состояния на соединение. Нужна «корзина» — создайте handle и передавайте его аргументом. Проверяйте права на handle при каждом вызове и опишите его срок жизни в description.
    КэшСтабильный порядок в tools/list, осмысленные ttlMs, cacheScope: "private" для ответов, зависящих от пользователя.
    АннотацииЧестные readOnlyHint и destructiveHint: по ним host решает, когда спрашивать подтверждение.
    Ввод от человекаДля подтверждений используйте elicitation в режиме form, для секретов, платежей и OAuth во внешних системах — режим url.
    ТранспортДля локального сервера — stdio, в stdout только MCP, логи в stderr. Для удалённого — Streamable HTTP без sticky-сессий, чтобы его можно было масштабировать горизонтально.
    ПроверкаMCP Inspector для ручной отладки, conformance-тесты для совместимости, тесты на инъекции в данных.

    Три API → один результат: оборачивать или перепроектировать?

    Частый случай: есть три утилитарных API, и бизнес-результат получается только их последовательным вызовом, когда выход первого становится входом второго. Нужно ли переделывать API под MCP?

    Короткий ответ. Сами API трогать не нужно: MCP-сервер — это адаптер поверх них. Перепроектировать стоит набор инструментов, то есть то, что видит модель. Если цепочка A → B → C всегда одинакова и нужна ради одного бизнес-результата, оберните её в один инструмент уровня задачи. Вызовы API и передача параметров между ними остаются в коде сервера.

    Пример: пользователь спрашивает «сколько нам должна ООО «Ромашка»?». Для ответа нужно найти клиента по ИНН (API 1), получить его договоры (API 2) и посчитать задолженность по ним (API 3).

    СитуацияРешение
    Порядок фиксирован, между шагами ничего не решаетсяОдин инструмент (Б). Это самый частый случай.

    Есть и третий путь, на стороне агента. Если host умеет выполнять код, модель пишет скрипт, который сам вызывает инструменты по очереди, и промежуточные данные не проходят через её контекст. Anthropic описывает этот подход в статье Code execution with MCP. Но это возможность конкретного host-а, а не гарантия протокола, поэтому основной сценарий надёжнее закрыть инструментом на сервере.

    Как это выглядит в коде сервера

    // псевдокод обработчика: старые API не меняются
async function getCustomerDebt({ inn, as_of }, ctx) {
  const customer = await api1.findCustomer(inn, ctx.upstreamToken);   // API 1
  if (!customer) {
    return toolError(`Клиент с ИНН ${inn} не найден. Проверьте ИНН ` +
                     `(10 цифр для юрлица) или найдите клиента через search_customers.`);
  }
  const contracts = await api2.listContracts(customer.id, ctx.upstreamToken); // API 2
  const debt = await api3.calculateDebt(contracts.map(c => c.id), as_of, ctx.upstreamToken); // API 3
  return {
    structuredContent: { customer: customer.name, ...debt },
    content: [{ type: 'text', text: summarize(customer, debt) }],
  };
}
// ctx.upstreamToken — собственные права сервера к API (или обмен токена),
// а не проброс токена MCP-клиента

    Когда всё-таки трогать сами API

    • N+1 запросов. API 3 считает долг только по одному договору, а договоров сотни. Нужен пакетный метод. Это оптимизация, MCP её не требует.
    • Состояние между вызовами живёт в сессии API. MCP теперь без сессий, поэтому состояние хранится в самой системе и передаётся явным handle.
    • Нет идемпотентности у записи. Серверу нужны ретраи, а без ключа идемпотентности повтор создаст дубль.
    • Нет прав от имени пользователя. API принимает только сервисную учётную запись, а отвечать нужно в рамках прав конкретного человека. Нужна делегация или обмен токена. Пробрасывать токен клиента запрещено.
    Итог. API остаются как есть. Инструменты проектируются от бизнес-задач: вход на языке пользователя (ИНН, а не customer_id), выход — готовый результат. Модели оставляют только те развилки, где действительно нужно её суждение.

    Как развивается стандарт

    Изменения проходят через SEP (Specification Enhancement Proposal) со статусами Draft → In-Review → Accepted → Final. Для статуса Final нужны эталонная реализация и conformance-тесты. Работу ведут рабочие группы: транспорты, реестр, SDK, Skills, триггеры и события, агенты и другие. Устаревшая функция живёт в спецификации минимум 12 месяцев. Проект развивается под эгидой Linux Foundation: в декабре 2025 года MCP передан в Agentic AI Foundation.

    Итог в одном абзаце. MCP-сервис — это адаптер между реальной системой и AI-приложением. Он описывает свои возможности как tools, resources и prompts, принимает самодостаточные JSON-RPC-запросы по stdio или HTTP, проверяет OAuth-токен, выданный именно ему, а когда ему нужен человек, отвечает через MRTR. Остальное — согласие пользователя, выбор инструментов и работу с моделью — берёт на себя host.

      Глава 1

      Проблема, которую решает MCP

      ИИ-ассистент полезен ровно настолько, насколько он подключён к данным и системам компании. До MCP каждое такое подключение было отдельным интеграционным проектом, своим для каждой пары «ИИ-приложение — система».

      Смотрите на схему

      анимация по шагам
      1. Без стандарта: 3 ИИ-приложения и 4 системы требуют 12 интеграций. Каждую нужно заказать, протестировать и сопровождать, а при смене поставщика ИИ всё делать заново.
      2. С MCP: каждая система подключается один раз через коннектор, каждое ИИ-приложение один раз поддерживает стандарт. Получается 7 компонентов вместо 12, и разрыв растёт с каждой новой системой.

      Что это значит для бизнеса

      • Стоимость интеграций растёт линейно, а не как произведение. 10 систем и 5 ИИ-инструментов — это 15 компонентов вместо 50 отдельных интеграций.
      • Независимость от поставщика ИИ. Коннекторы к вашим системам работают с любым совместимым ИИ-приложением, и смена поставщика не обнуляет вложения.
      • Готовые коннекторы. Многие поставщики SaaS уже публикуют MCP-коннекторы к своим продуктам: их не нужно разрабатывать.
      • Единые правила контроля. Доступ, согласие и аудит устроены одинаково для всех подключений.
      Аналогия. MCP для ИИ — то же, что единый формат электронных документов для документооборота. Один раз настроили — и работаете со всеми, вместо того чтобы договариваться о формате с каждым контрагентом отдельно.
      Глава 2

      Участники и зоны ответственности

      В любой схеме с MCP три участника. Для решений важно понимать, кому каждый из них принадлежит и за что отвечает.

      УчастникЧто это и за что отвечает
      ИИ-приложениеЧат-ассистент, среда разработки, корпоративный агент. Покупается у поставщика или разрабатывается своими силами. Отвечает за работу с моделью, интерфейс и запрос согласия сотрудника.
      КоннекторВ терминах стандарта это MCP-сервер, «переходник» к конкретной системе. Бывает готовым от поставщика системы, открытым или собственной разработки. Определяет, какие операции доступны, проверяет права и связывается с системой.
      Ваши системыУчётная система, CRM, хранилища документов, внешние сервисы. Не меняются: коннектор работает поверх существующих интерфейсов.

      Пройдёмся по схеме

      нажмите на шаг
      1. ИИ-приложение координирует работу: решает, какие коннекторы подключены и что показать модели.
      2. Коннектор к внутренней системе можно разместить внутри периметра компании, и данные не покинут контур.
      3. Коннектор к облачному сервису обычно предоставляет сам поставщик сервиса.
      4. Существующие системы остаются как есть: коннектор использует их текущие интерфейсы.
      5. Модель не подключается к системам напрямую. Она работает только с тем, что ей предоставило ИИ-приложение.
      Принцип изоляции. Коннекторы не видят переписку сотрудника целиком и не видят друг друга. Переносить данные между ними может только ИИ-приложение, и только с согласия пользователя.

      Где размещать коннекторы. Внутри периметра — для внутренних систем и чувствительных данных. В облаке — для SaaS-сервисов. От этого выбора зависят требования информационной безопасности и стоимость эксплуатации.

      Глава 3

      Что умеет коннектор

      Коннектор предлагает ИИ три вида возможностей. Они различаются тем, кто решает об их использовании, и от этого напрямую зависит политика контроля.

      ВозможностьПример · кто решает · как контролировать
      Действия«Создать счёт», «найти договор», «рассчитать задолженность». Решает модель по ходу диалога. Необратимые действия подтверждает человек.
      ДанныеСправочники, документы, карточки клиентов. Подбирает приложение. Контроль — права доступа к данным.
      СценарииУтверждённые шаблоны работы: «сверка с контрагентом», «отчёт по продажам за период». Запускает сотрудник. Сценарии утверждает владелец процесса.

      Кто что запускает

      нажмите на шаг
      1. Модель видит список действий с описаниями и сама решает, когда какое вызвать.
      2. Приложение добавляет в работу нужные данные: открытый документ, карточку клиента.
      3. Сотрудник выбирает готовый сценарий, например «Сверка с контрагентом за квартал».
      Практический вывод. Сценарии помогают тиражировать лучшие практики. Процедуру сверки или подготовки отчёта описывают один раз, и она становится доступна каждому сотруднику в ИИ-ассистенте в одинаковом, утверждённом виде.
      Глава 4

      Как проходит один запрос

      Сотрудник спрашивает ассистента: «Сколько нам должна ООО «Ромашка»?» Проследим, что происходит между вопросом и ответом.

      От вопроса до ответа

      нажмите на шаг
      1. Сотрудник задаёт вопрос обычным языком.
      2. Модель видит доступные действия коннекторов и выбирает подходящее: «задолженность клиента».
      3. ИИ-приложение передаёт запрос коннектору. Если действие меняет данные, сначала запрашивается согласие сотрудника.
      4. Коннектор проверяет права сотрудника и выполняет запрос к учётной системе.
      5. Система возвращает данные.
      6. Коннектор отдаёт итог и детализацию по договорам.
      7. Сотрудник получает ответ с цифрами из системы.

      Что важно для руководителя

      • У модели нет прямого доступа к системам. Она может только выбирать из операций, которые заранее определены в коннекторе.
      • Каждое действие оставляет след: кто спросил, какая операция, с какими параметрами. На этом строится аудит.
      • Ответ опирается на данные системы, а не на «память» модели. Поэтому риск выдуманных цифр ниже.
      • Сбои объяснимы. Если данных нет или операция невозможна, коннектор возвращает понятное объяснение, и ассистент уточняет запрос у сотрудника.
      Глава 5

      Контроль человека над важными действиями

      Для необратимых операций — платежа, удаления, изменения договора — в стандарте есть механизм, при котором коннектор приостанавливает операцию и запрашивает подтверждение у сотрудника.

      Подтверждение операции

      нажмите на шаг
      1. Ассистент просит коннектор выполнить операцию, меняющую данные.
      2. Коннектор не выполняет её сразу, а отвечает, что нужно подтверждение, и описывает, что именно будет сделано.
      3. Сотрудник видит форму с описанием операции. Модель ответить за него не может.
      4. Сотрудник подтверждает. Он может и отказаться, тогда операция не выполнится.
      5. Запрос отправляется повторно вместе с подтверждением.
      6. Коннектор проверяет, что подтверждение относится именно к этой операции, и выполняет её.
      7. Результат возвращается ассистенту.
      • Подтверждение нельзя подменить. Коннектор защищает состояние операции, поэтому согласие на одну операцию не переносится на другую.
      • Секреты через такие формы запрашивать запрещено: пароли, ключи, платёжные данные. Для этого сотрудника перенаправляют на страницу самой системы.
      • Долгие операции (формирование отчёта, выгрузка) выполняются в фоне: ассистент получает номер операции и следит за её статусом.
      Как использовать в процессах. Этот механизм — техническая основа для правил «четырёх глаз» и лимитов. Например, платежи выше порога проходят только с подтверждением ответственного.
      Глава 6

      Доступ: кто и к чему

      Для облачных коннекторов стандарт опирается на OAuth 2.1. Это тот же механизм, что работает при входе «через корпоративную учётную запись». Схема выглядит так.

      Первое подключение

      нажмите на шаг
      1. Ассистент обращается к коннектору впервые.
      2. Коннектор отказывает и сообщает, где получить доступ.
      3. Сотруднику открывается привычная страница корпоративного входа.
      4. Сотрудник входит и видит, к чему ассистент просит доступ.
      5. Система входа выдаёт пропуск, который действует только для этого коннектора.
      6. Дальше каждый запрос идёт с пропуском.
      7. Коннектор проверяет пропуск и права сотрудника и только потом выполняет запрос.

      Четыре свойства, важные для бизнеса

      • Права ассистента равны правам сотрудника. Ассистент действует от имени конкретного человека и в пределах его прав. Смена роли или увольнение ограничивают доступ автоматически.
      • Пропуск привязан к коннектору. Пропуск, выданный для одной системы, нельзя использовать в другой.
      • Минимальные права на старте. Дополнительные права запрашиваются только тогда, когда они действительно нужны.
      • Централизованный контроль. Доступ выдаёт корпоративная система входа, и там же его можно отозвать.
      Для корпоративного развёртывания есть расширения стандарта: доступ, которым централизованно управляет корпоративный провайдер учётных записей, и доступ между сервисами без участия пользователя.
      Глава 7

      Риски и как ими управлять

      ИИ с доступом к системам — это новый класс рисков. Стандарт не устраняет их автоматически: защита складывается из правил ИИ-приложения, качества коннекторов и политик компании.

      Карта рисков

      красные кристаллы на схеме
      1. Непроверенный коннектор может содержать скрытые инструкции для модели.
      2. Вредный текст в данных — письме, документе, заявке клиента — может выдавать себя за команду ассистенту.
      3. Коннектор не должен передавать пропуск сотрудника дальше, в другие системы.
      4. Посредник не должен действовать от имени пользователя без его отдельного согласия.
      5. Подмена адресов при подключении может открыть доступ во внутреннюю сеть.
      6. Установить коннектор на компьютер — значит запустить чужую программу.
      7. Знание номера операции не должно давать доступа к ней: проверяется, кто её владелец.
      8. Политика согласий определяет, что ассистенту разрешено без вопросов, а что — только с подтверждением.

      Ошибочные действия ИИПодтверждение необратимых операций, лимиты, на старте режим «только чтение».
      Манипуляция через данныеСодержимое документов и писем — это данные, а не указания. Критичные действия только с подтверждением.

      Глава 8

      Проектируйте под бизнес-операции, а не под API

      Самая частая ошибка внедрения — механически превратить существующие API в набор команд для ИИ. Существующие системы менять не нужно, но операции коннектора стоит проектировать от бизнес-задач.

      Пример: чтобы узнать задолженность клиента, нужно обратиться к трём системам по очереди: найти клиента, получить его договоры, посчитать долг.

      Вариант А: три технические операции

      данные между шагами переносит модель
      1. Коннектор повторяет устройство систем: три отдельные операции.
      2. Первое обращение.
      3. Система 1.
      4. Промежуточный результат возвращается модели.
      5. Модель должна правильно продолжить цепочку и без ошибок перенести данные. Это лишнее время, стоимость и риск ошибки.
      6. Второе обращение.
      7. Система 2.
      8. Снова через модель.
      9. Третье обращение.
      10. Система 3.
      11. Итог получен после трёх обращений модели к коннектору.

      Вариант Б: одна бизнес-операция

      цепочку ведут правила коннектора
      1. Коннектор предлагает операцию на языке пользователя: «задолженность клиента по ИНН».
      2. Одно обращение.
      3. Внутри коннектора: система 1…
      4. …система 2…
      5. …система 3. Данные между шагами передают правила коннектора, а не модель.
      6. Модель получает только итог.
      А: три операцииБ: одна операция
      Скорость3 цикла работы модели1 цикл
      СтоимостьВыше: промежуточные данные проходят через модельНиже
      НадёжностьМодель может ошибиться при переносе данныхПравила заданы в коннекторе
      КонтрольЦепочку сложнее проверитьОдна запись в журнале на один бизнес-результат
      Правило. Одна операция коннектора — один бизнес-результат, сформулированный на языке пользователя. Существующие системы остаются как есть. Дорабатывать их имеет смысл, только если не хватает возможностей: нет пакетной обработки, нельзя работать от имени конкретного сотрудника, повтор операции создаёт дубли.
      Глава 9

      Масштаб, надёжность и зрелость стандарта

      Для решения о внедрении важно, как решения на MCP масштабируются и насколько устойчив сам стандарт.

      Нагрузка распределяется

      любой запрос — любой копии
      1. Первый запрос обрабатывает копия A.
      2. Ответ.
      3. Следующий запрос уходит на копию C, и это нормально.
      4. Ответ.
      5. Третий запрос уходит на копию B.
      6. Ответ.
      • Масштабируется как обычный веб-сервис. С версии 2026-07-28 протокол не требует удерживать сессию: любой запрос может обработать любая копия коннектора. Выросла нагрузка — добавили копий.
      • Открытый стандарт с нейтральным управлением. MCP развивается под эгидой Linux Foundation (Agentic AI Foundation), изменения проходят открытый процесс.
      • Предсказуемые изменения. Устаревшие функции сохраняются минимум 12 месяцев, так что на миграцию есть время.
      • Широкая поддержка. Официальные библиотеки для основных языков (TypeScript, Python, C#, Go, Rust, Java и другие), официальный каталог коннекторов, поддержка у ведущих поставщиков ИИ-приложений.
      Что учесть. Стандарт молодой и быстро развивается: в 2026 году вышло существенное обновление. Заложите в план обновление коннекторов и выбирайте поставщиков, которые следят за версиями спецификации.
      Глава 10

      С чего начать

      Коннектор — это небольшой сервис с понятной структурой. На схеме он показан в разобранном виде, а ниже — план пилота и вопросы, которые стоит задать команде и поставщикам.

      Из чего состоит коннектор

      нажмите на шаг
      1. Раскладываем коннектор по слоям.
      2. Приём запросов: защищённый канал связи.
      3. Проверка доступа: кто спрашивает и что ему разрешено.
      4. Каталог операций: что именно доступно ИИ. Здесь проходит граница возможностей ассистента.
      5. Бизнес-логика: правила и связь с существующими системами.
      6. Контроль и аудит: журнал всех обращений.

      План пилота

      1. Выберите 2–3 сценария с измеримым эффектом: частые, рутинные, с понятной метрикой (время ответа клиенту, трудозатраты на сверку).
      2. Проведите инвентаризацию: какие системы нужны и есть ли для них готовые коннекторы у поставщиков.
      3. Начните в режиме «только чтение»: ассистент ищет и отвечает, но ничего не меняет.
      4. Утвердите политики: белый список коннекторов, права, журнал, правила подтверждений.
      5. Добавьте действия с подтверждением: операции, меняющие данные, — только под контролем человека.
      6. Масштабируйте: новые сценарии и системы по результатам метрик.
