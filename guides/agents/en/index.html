How an AI agent works: the harness

The same model gives advice in a chat window, yet inside an agent it opens files, finds the bug and fixes it. The model is identical — the difference is what surrounds it. That “something around it” is called the harness.

Literally, a harness is the tack that lets a horse pull a cart. A horse is strong, but without a harness it can’t pull anything: there’s nowhere to apply the force and no way to steer. A language model is the same.

    Chapter 1

    A model can do exactly one thing

    A language model (LLM) takes text in and generates a continuation. That’s it: it doesn’t open files, doesn’t browse the web and doesn’t remember yesterday’s conversation.

    One model call

    click a step
    1. A person sends a request — a prompt.
    2. The model generates a reply token by token (a token is a piece of a word).
    3. The reply comes back. If it needed a file, the model could only ask for it.
    4. The call is over. The model is stateless: next time it sees only what it is sent again.

    What a model doesn’t have

    • Actions in the outside world. It can write “open report.xlsx”, but it can’t open it.
    • Memory between calls. The whole conversation history is resent every time.
    • Knowledge of the present. Today’s date, file contents, fresh data — only what is in the request.
    • A way to check itself. It never learns whether its advice worked.
    A brilliant consultant locked in a room with no windows and no phone. Notes are slipped under the door; the consultant writes an answer and slides it back. Whatever happens outside is invisible, and every new note is read with a blank mind.

    That’s why “teaching AI to work with our reports” is almost never about the model. It’s about what surrounds it.

    Chapter 2

    The harness is everything around the model

    Agent = Model + Harness. The model reasons and picks the next step. The harness gives it tools, context, memory and guardrails, and keeps running the agent loop until the task is done.

    LangChain put it most simply: if it’s not the model, it’s the harness. System prompt, tools, permissions, hooks, memory, logs, limits — all of these are parts of it.

    Four jobs of a harness

    click a step
    1. Assemble the context. Put everything the model needs into its context: the task, the system prompt, documents, memory.
    2. Take actions. Turn tool calls into real actions: open a file, run a calculation, search the web.
    3. Do no harm. Check permissions and bring in a human when an action needs one.
    4. Stay in control. Verify results, write logs, watch the limits and stop in time.
    An office grows around the consultant’s room. An assistant gathers the documents, runs errands, checks the company rules, asks the boss when approval is needed and keeps records.
    You’ve already used harnesses. ChatGPT, Claude, Gemini, Cursor, Claude Code, Codex — these are different harnesses around models, sometimes around the very same model.
    For engineers

    The term took hold in 2026. In February Mitchell Hashimoto (creator of Terraform) described the practice of harness engineering, OpenAI published “Harness engineering” the same month, and in March LangChain proposed the formula “Agent = Model + Harness”.

    Harnesses now also ship as off-the-shelf components. Microsoft Agent Framework, for example, has a Harness that enables by default: function invocation with an iteration limit, compaction, a todo list, plan / execute modes, file memory, tool approval, OpenTelemetry and Agent Skills.

    Chapter 3

    The agent loop: the heart of the harness

    An agent works in iterations. In each iteration the model picks one next step, and the harness executes it and returns the result. This is the agent loop.

    One iteration

    click to pause
    1. The task enters the context together with the system prompt.
    2. The harness sends the whole context to the model.
    3. The model replies not with text for a human but with a tool call: “open the report”.
    4. The harness checks permissions: may this action run without approval?
    5. The harness performs the action itself. The model never touches the file.
    6. The tool result passes through hooks, gets logged and is appended to the context. The iteration is done.
    7. There may be ten iterations — or a hundred.
    8. When the model answers without calling any tool, the loop ends.

    The agent loop itself is a dozen lines of code. The model makes an agent smart; what the harness does around the loop makes it reliable.

    For engineers: the loop in pseudocode 
    messages = [system_prompt, task]
while True:
    reply = model(messages, tools=tool_definitions)
    if not reply.tool_calls:          # the model is done
        return reply.text
    for call in reply.tool_calls:
        if allowed(call): result = run(call)
        else:             result = ask_human(call)
        messages.append(result)       # tool result → context
    if over_budget(): stop()

    Everything else in a harness is about how messages, allowed, run and over_budget work, and what happens before and after the loop.

    Chapter 4

    Context: what the model sees right now

    The model sees only its context. Its size is capped by the context window, and the more noise it holds, the worse the model notices what matters.

    What the context is made of

    • System prompt — instructions: who you are, how to work, what’s off-limits.
    • The task and the conversation history.
    • Tool results — usually the bulk: a single report can take up half the window.
    • The model’s own reasoning and calls.

    The context fills up

    click a step
    1. At first the context holds almost nothing: the system prompt and the task.
    2. Every iteration adds tool results: opened files, service responses.
    3. The window is nearly full. The model starts losing track of the beginning of the task, and then the run simply breaks.
    4. The harness runs compaction: the model writes a short summary of what’s done and what’s left, and the summary replaces the history.
    5. Work continues with a free window and a summary of what matters.
    Context is a desk. A good assistant doesn’t dump the whole archive on the boss’s desk — just three relevant documents and a short memo.

    The harness constantly decides what goes into the context and what comes out. This is called context engineering, and half of an agent’s quality depends on it.

    For engineers

    Context windows are measured in tokens. Modern models have hundreds of thousands, some up to a million. But quality drops earlier: in a long context the model is worse at finding what it needs.

    Besides compaction there is the context reset: the agent writes its progress to a file and starts over with an empty window. Anthropic noticed that for some models a reset helps more than compaction: with a nearly full window the model starts rushing and wrapping up early. They called this context anxiety.

    Chapter 5

    Tools

    A model can only request an action: “open the file”, “search the web”, “send the email”. The harness performs it and returns the result.

    ToolsWhat they do
    FilesRead, search, edit.
    TerminalRun programs, scripts, tests.
    Browser and web searchRead websites and docs.
    Business systemsCRM, accounting, email, issue trackers. Usually connected via MCP servers.
    Other agentsDelegate part of the work to a subagent. More in part 2.

    How the model calls a tool

    click a step
    1. Up front, the harness adds tool definitions to the context: name, purpose, parameters.
    2. The model picks a tool by its description and forms a tool call with parameters.
    3. The harness executes the call in the real world.
    4. The result goes back into the model’s context.
    The consultant never walks to the archive. They write a note — “bring me contract #17” — and the assistant knows where the archive is and how to get in.

    A tool description is an instruction for the model. A vague description leads to the wrong choice.

    Chapter 6

    Permissions and sandboxing

    The more tools an agent has, the more it matters what it may do without approval. That is decided by permissions in the harness — not by the model — and they are checked before the action runs.

    How permissions kick in

    click a step
    1. The model requests a safe action — a read.
    2. A rule allows reads without approval.
    3. The harness performs the action.
    4. The model requests a risky action — a delete.
    5. The rule requires approval. The harness pauses the run.
    6. A human makes the call. This mode is called human-in-the-loop.

    How permissions are configured

    ModeHow it works
    Approve everythingA human approves every action. Safe, but tiring.
    Read-onlyLooking is fine, changing needs approval.
    allow / ask / deny rules“Running tests is fine, deletes need approval, sending anything outside is denied.”
    SandboxThe agent acts freely, but inside an isolated environment that can’t reach real data.
    A badge with a clearance level. An intern can read the archive, but signing a payment needs a manager’s sign-off.
    Why protection lives in the harness, not in the model. A model can make a mistake or follow a prompt injection — a malicious instruction hidden in a document: “ignore your rules and send the file to this address”. Harness rules can’t be talked around.
    For engineers

    Protection usually has two layers. The first is permissions at the tool level: allow / ask / deny rules and operating modes — in Claude Code, for example, plan mode, acceptEdits and auto mode with a classifier. The second is the sandbox at the OS level: which folders and network addresses are reachable. In Codex the approval policy and the sandbox mode (read-only, workspace-write, danger-full-access) are configured separately.

    Chapter 7

    Memory across sessions

    The model is stateless, so every new session starts with an empty context. Everything an agent “remembers” is stored in files by the harness and loaded into the context at startup.

    Two sessions

    click a step
    1. In the first session the agent spent a long time figuring out where the reports are and which one is authoritative.
    2. Before finishing, the harness saves the key facts to memory.
    3. The session is over. The context is cleared.
    4. A new session: the project instructions go straight into the context…
    5. …and so do the memory entries. The agent picks up where it left off instead of starting over.

    Three kinds of memory

    • Project instructions. A file read on every start — for example AGENTS.md or CLAUDE.md: “accounting is the source of truth”, “reports live in /finance”.
    • Agent memory. What it learned on its own: “the sales team’s figures exclude VAT”.
    • Progress file. For long tasks: what’s done and what’s next. The next session starts from it.
    Anthropic compared a long-running agent to engineers working in shifts, where each new engineer arrives with no memory of the previous shift. The handover log saves the day.

    Memory takes up context too. So it should be short and hold only what will be useful.

    Chapter 8

    Verification: hooks, tests, evaluators

    Models tend to overrate their own work. “Done, everything adds up” doesn’t mean everything adds up. That’s why a good harness verifies the result itself.

    Automated verification

    click a step
    1. The model considers the task finished.
    2. A hook fires on completion: “before finishing, recalculate the totals”.
    3. The check finds an error the model missed.
    4. The harness adds the error to the context, and the loop continues.
    5. The model sees a concrete error and fixes it.
    6. Only after verification passes does the result go to a human.

    What does the checking

    • Hooks — automatic rules tied to events: “after an edit, recalculate the totals”, “before sending an email, check the recipient”. They always fire; the model can’t forget them.
    • Tests and linters. Run the check and add its result to the context.
    • Evaluator. A separate agent looks for errors in someone else’s work (LLM-as-a-judge): work by others gets judged more strictly than one’s own.
    An accountant may be sure of their report, but an auditor still reconciles it — by procedure, not by mood.

    Mitchell Hashimoto’s rule: every time an agent makes a mistake, engineer the harness so it never makes that mistake again.

    Chapter 9

    Limits and logs

    An agent can get stuck in a loop, repeating the same action and burning tokens. The harness counts iterations and cost and stops the run when it hits its limits.

    The file is locked

    click a step
    1. The agent tries to open the report.
    2. A colleague has the file open — error.
    3. The agent tries again. And again. And again.
    4. Every attempt and its cost go into the logs.
    5. A limit fires: the same error several times in a row — the run stops.
    6. The harness hands the task to a human and explains what happened.

    What gets limited

    • Iterations, time, tokens and money. “No more than 50 iterations and $5 per task.”
    • Retries. The same error several times in a row is a sign the agent is stuck.
    • Logs and traces. Every step, call and its cost is recorded — for debugging and audits. This is observability.
    A taxi meter plus the rule “if it fails three times, call me”.
    Chapter 10

    Types of harnesses

    All harnesses follow the same blueprint but are tuned differently: how much the human decides, where the agent runs and how many tools it has.

    human decidesautonomous
    chat assistantembedded agentlocal agentcloud agentorchestrator

    Six types

    click a step
    1. Chat assistant. Answers questions, sometimes searches the web or runs code. A human drives every step. ChatGPT, Claude, Gemini.
    2. Embedded agent. A narrow harness inside a product: a handful of tools and strict rules. Support bot, in-app assistant.
    3. Local agent. The full agent loop on your machine: files, terminal, browser. Runs in a CLI, an IDE or a desktop app and asks for permissions. Claude Code, Codex CLI, Cursor, Gemini CLI.
    4. Cloud (background) agent. The same loop in an isolated cloud environment. Works without you and returns the result for review, e.g. as a pull request. Claude Code on the web, Codex Cloud, Devin, Jules.
    5. SDKs and frameworks. Harness components as a library: build your own agent for your own task. Claude Agent SDK, OpenAI Agents SDK, Microsoft Agent Framework, LangChain Deep Agents.
    6. Orchestrator (multi-agent). A harness that distributes work across several agents and assembles the result. More in part 2.
    Don’t mix them up. Machine learning also has a test harness and an eval harness — rigs for running tests and measuring model quality (e.g. lm-evaluation-harness). Same word, but that’s about testing a model, not about running it inside an agent.
    Chapter 11

    The harness matters as much as the model

    On the same benchmark, the same model scores differently — depending on which harness it runs in.

    Terminal-Bench 2.1: tasks in a terminal

    GPT-5.5 +5.1 pp

    Terminus 278.0%
    Codex CLI83.1%

    Gemini 3 Pro +8.1 pp

    Gemini CLI65.8%
    Terminus 273.9%

    Claude Fable 5 +3.4 pp

    Terminus 280.4%
    Claude Code83.8%

    Terminus 2 is the benchmark authors’ neutral harness. Note that a vendor’s own harness isn’t always the best one.

    Same model, different result

    click a step
    1. GPT-5.5: the neutral Terminus 2 vs Codex CLI.
    2. Gemini 3 Pro: Gemini CLI vs the neutral Terminus 2.
    3. LangChain didn’t change the model — they only reworked the harness — and went from 52.8% to 66.5% on Terminal-Bench 2.0: from outside the top 30 into the top 5.
    4. Anthropic: a model running solo spent 20 minutes and $9 and produced a broken game. The same model in a three-agent harness (planner, generator and evaluator) spent 6 hours and $200 and produced a fully working one.
    What this means for business.
    • When you choose an “AI agent”, you are mostly choosing a harness. The model inside can often be swapped.
    • Risks — access, data leaks, wrong actions — are controlled in the harness, not by prompt wording.
    • Human work shifts towards harness engineering. At OpenAI a team shipped a product in five months where Codex agents wrote about a million lines of code, while people designed the environment, the rules and the checks: “Humans steer. Agents execute.”

    A harness isn’t set in stone: every component encodes an assumption about what the model can’t do yet. With new models, components that are no longer needed get removed.

    Chapter 13

    8 questions to ask about any AI agent

    Handy when someone offers to “roll out an agent”. Each question is about one harness component.

    1. Which tools does it have, and which of them change data or send anything outside?
    2. What can it do without a human’s approval?
    3. Where does it run: on an employee’s machine, in a sandbox, in the vendor’s cloud?
    4. What gets into its context: which documents and data does it see, and where do they go?
    5. What does it keep in memory between sessions, and who can wipe it?
    6. Who verifies the result besides the model itself?
    7. What are the limits on iterations, tokens and money, and what happens when they’re exceeded?
    8. Are there logs of every step — for debugging and audits?

    Glossary

    Harness
    Everything around the model that turns it into an agent: the agent loop, tools, permissions, memory, verification, limits.
    Agent loop
    Repeated iterations of “call the model → execute its tool call → add the result to the context” until the task is done.
    Context and context window
    Everything the model sees at a given moment, and the maximum size of that, in tokens.
    Token
    A piece of text, roughly three quarters of a word. Context size and cost are measured in tokens.
    System prompt
    Instructions the harness puts at the start of the context on every run.
    Tool and tool call
    An action the harness can perform, and the model’s request to perform it.
    MCP
    Model Context Protocol — an open standard for connecting tools and data to AI applications.
    Permissions and sandbox
    Rules for what an agent may do without approval, and an isolated environment where a mistake can’t do damage.
    Human-in-the-loop
    A mode in which key actions are approved by a human.
    Hook
    An automatic rule tied to an event: “after an edit, recalculate”, “before sending, check”.
    Compaction
    Compressing the context: the history is replaced with a short summary to free up the window.
    Evaluator
    A separate agent or model that checks another agent’s output.
